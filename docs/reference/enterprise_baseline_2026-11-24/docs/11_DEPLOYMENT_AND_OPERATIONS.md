# Deployment and operations
## Environments
Local development with disposable MySQL and synthetic data; CI isolated; staging separate credentials/database and test tenants; production Linux VPS with restricted access. A single VPS may host API/worker/frontend/MySQL initially, but it is not high availability. Staging may share hardware only for early pilot if isolated and resource-bounded; prefer separate host before critical production. Proposed domains `conex360.sysconex.com`, `api.conex360.sysconex.com` (or same-origin /api preferred for simplicity), `staging.conex360.sysconex.com`; DNS and certificate ownership not verified.

## Proposed deployment design
Docker Compose with reverse proxy TLS, immutable API/worker/Next.js Node runtime images, internal network DB, persistent DB/file volume, restricted migration job. Pin versions; do not expose 3306. Only HTTPS/public redirect and controlled SSH as needed. Firewall, SSH keys, patch OS, service accounts, minimal container privileges, resource and connection pool limits. Use secret injection; separate app, migration, backup credentials. No secret values in sample env file. Health checks: liveness process only, readiness necessary dependencies. Log rotation/disk monitoring. Configure reverse proxy limits and timeouts; secure headers. Cert renewal tested. Private registry and least-privilege deployment key.

## Release runbook
1. Review PR and migrations, CI results, release notes and change scope; verify staging against production-like schema. 2. Verify offsite backup/restore readiness and maintenance window; prevent competing migrator. 3. Run controlled versioned migration with checksum, log and lock. 4. Deploy immutable tagged application, run readiness and scoped smoke tests. 5. Verify posting/reconciliation and monitoring; document release. 6. If failure, stop affected posting/rollback application only if schema compatible; use compensating migration or approved restore for data changes. Never blindly roll back MySQL DDL or overwrite unrelated tenants.

## Backup and restore
Encrypted offsite full backups plus frequent/continuous binlog archive for point-in-time recovery. Separate credentials and storage, retention and key-recovery policy. Proposed RPO <=15 min, RTO <=4 h subject to measured restore and customer agreement. Backup success logs are not proof: restore in isolated environment and validate stock, journal, open items, transfer transit, WIP, payments and offline checkpoints. Document exact tools/commands after infrastructure choice. Tenant-specific restore: isolate full snapshot, extract consistent scoped graph, map global references, reconcile external payments/offline ops and later events; never restore one tenant by wiping whole platform. Design/runbook/test before offering tenant recovery service.

## Monitoring and incidents
Track uptime, error/latency, DB pool/lock waits/deadlocks, disk space, CPU/RAM, slow queries, backup age, outbox lag, offline backlog, overdue transit and reconciliation differences. Alerts actionable, no PII. Incident sequence: classify, contain (disable affected posting feature if integrity threatened), preserve logs/audit, communicate, investigate scoped data, approve correction/replay, verify reconciliation, record postmortem. For failed transfer, never edit balance manually; inspect original idempotency, document and movements, resolve with approved linked correction. For external capture uncertainty, query provider before retry. For lost offline device, revoke and reconcile quota/cash before release.

## Scaling
Measure actual tenants, outlets, tills, SKU/lot counts, transaction/report mix and retention; load test pilot 4 vCPU/8 GB starting assumption. Scale DB/resources before splitting modules; later separate DB, workers/replica, tenant routing/sharding only with approved design. No capacity or uptime guarantee from VPS size alone.

## Next.js production hosting
Build a multi-stage frontend image with pinned Node LTS, locked dependencies and Next.js production build. Standalone output is proposed; if used, include required public and .next/static assets and validate the runtime startup. Run as non-root, expose only the internal frontend port and place Nginx in front. Route `/api/` to ASP.NET Core and other application routes/assets to Next.js; keep `/api/` reserved and test exact path handling and forwarded HTTPS headers. Frontend never connects directly to MySQL. Supply server-only runtime API URL/configuration where needed; public build-time variables must contain no secrets. Disable intermediary caching for authenticated HTML/RSC/API responses, and allow safe caching of immutable public assets. Confirm memory budgets, health checks, graceful shutdown, rollback and smoke tests for the additional Node process. Do not assume static export or a CDN-only host supports server-side features.
